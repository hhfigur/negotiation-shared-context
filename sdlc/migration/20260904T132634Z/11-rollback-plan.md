## Rollback strategy for the proposed Stage 3 `APPLY` migration (not yet executed — this is guidance for if/when it runs)

Per migration principle #11 ("keep the migration reversible") and the master prompt's Stage 3.1 instructions:

1. **Dedicated branch per repository.** Each of the three repos gets its own migration branch (naming to match each repo's existing convention — not independently determined this pass, since no feature-branch history was available to infer a pattern from; default to something like `migration/sdlc-overlay` pending owner confirmation). No direct commits to `main` in any repo.
2. **Additive-only changes.** Every item in `08-migration-plan.md` Phases A-D is either a brand-new file (trivial rollback: delete the file / don't merge the branch) or a merge into an existing file that **adds** a section without deleting existing content (rollback: `git revert` the specific commit, or hand-edit out the added section — both are low-risk since nothing existing was removed). Phase E's factual corrections (`09-proposed-file-diffs.md`) are the only true "edit existing content" changes, and each is a small, isolated diff with its own `git revert` path already listed per-diff.
3. **No destructive operations anywhere in this plan.** No file is deleted, renamed, or overwritten wholesale (`ALLOW_DELETIONS_OR_RENAMES: false` honored throughout `08-migration-plan.md`/`09-proposed-file-diffs.md`). The furthest any proposal goes is `SUPERSEDE_LATER` (an annotation, not a removal) on stale Controller/governance docs.
4. **Plugin install/uninstall is reversible by design.** `/plugin marketplace add` + `/plugin install` (Phase A) has a documented inverse (`/plugin uninstall`, remove the marketplace registration) — no repository file is touched by installing a *local* plugin from `shared-context/tooling/claude-marketplace/`.
5. **No hook is activated.** `HOOK_CANDIDATES.md` (Phase A) is documentation only; nothing in any `settings.json` changes as part of this migration, so there is no hook-related rollback surface at all.
6. **No production/remote system is touched.** No Supabase migration is applied, no deploy is triggered, no secret is written or read beyond names — consistent with `ALLOW_PRODUCTION_CHANGES: false`. The one Supabase-related action recommended (re-verifying which project the MCP tool actually reaches, `10-conflicts-and-decisions.md` validation item 1) is explicitly read-only.
7. **Per-branch rollback granularity.** Because frontend, backend, and shared-context changes live on independent branches in independent repos, any one repo's migration branch can be abandoned without affecting the other two — consistent with "preserve separate frontend and backend repositories and working windows."
8. **Working-tree safety.** Before any Stage 3 edit, re-run `git status` in the target repo (not just trust this analysis's Stage 0 snapshot, which is now stale the moment any commit happens elsewhere) — especially important for `negotiation-buddy`, which had 4 real uncommitted files at scan time; those must be re-checked (still present? committed? changed further?) before Stage 3 touches anything in that repo, per "preserve uncommitted user work."

### C3 — Task-closing mechanism: four coexisting variants — **RESOLVED 2026-09-04, with one unresolved implementation gap**

- `shared-context/.claude/skills/close-task/SKILL.md` (targets `docs/wiki/*`, has a known path bug)
- `shared-context/.claude/skills/close-task-dev/SKILL.md` (referenced by both frontend and backend `CLAUDE.md` "Delivery Workflow" sections as the Step 4 mechanism)
- `negotiationcoach-backend/.claude/skills/close-task/SKILL.md` (local, real content, distinct from shared-context's)
- `negotiation-buddy/.claude/skills/close-task/SKILL.md` (local, real content, targets nonexistent `docs/api-catalog.md`/`docs/db-map.md` paths in that repo)
- **Decision basis — owner statement (2026-09-04)**: "The canonical closure mechanism for all new SDLC-managed work is `/negotiation-ai-sdlc:close-change`. Existing close-task variants are classified as LEGACY. They must not be used for new SDLC-managed changes. Do not delete legacy variants during the first migration pass. Preserve them temporarily for traceability and rollback. close-change must enforce the SDLC closure gate." The specified minimum closure gate: `intent.md`/`spec.md`/`plan.md` exist and are accepted; implementation is complete; `verification.md` exists and passes; `review.md` exists and is accepted; no open CRITICAL finding; no open HIGH finding; traceability is complete — plus `release.md`/`outcome.md` where the change type requires them.
- **Resolution**: all four variants above are now formally classified **LEGACY** — not used for any new `sdlc/changes/<id>/`-managed work, not deleted, not modified, kept solely for traceability of already-closed items and as a rollback path. `/negotiation-ai-sdlc:close-change` is canonical for new work going forward.
- **Unresolved implementation gap found on direct read of `close-change/SKILL.md` this pass**: the Skill as currently written in the kit is **not** a pre-release closure gate — it is the **outcome-measurement Skill**, invoked at the Development Controller's `Released → Measure outcome` state (confirmed against `DEVELOPMENT_CONTROLLER.md`'s state-machine table). Its workflow creates/updates `outcome.md`, compares target vs. actual outcome measures, and reaches a `CLOSE`/`MONITOR`/`ITERATE`/`ROLL_BACK`/`CREATE_INCIDENT` decision. It does **not** itself re-check that `intent.md`/`spec.md`/`plan.md` are accepted, that `verification.md` passes, that `review.md` is accepted, or that no CRITICAL/HIGH finding is open — it assumes those already happened.
  - **Charitable reading**: the kit's Development Controller state machine only allows reaching `close-change` after sequentially passing through `capture-intent → create-spec → create-plan → implement-change → verify-change → review-change → release`, each with its own entry gate (confirmed by direct read of all four Skills plus the Controller). Under this reading, the "SDLC closure gate" the owner describes is already enforced — just **distributed** across the chain rather than centralized in one Skill, and `close-change` is correctly the *final* link (outcome), not a *redundant* final gate-check.
  - **Literal reading of the owner's rule 5** ("close-change must enforce the SDLC closure gate") plausibly wants `close-change` to *itself* re-verify the full checklist as a defense-in-depth measure (e.g., against a manually-edited `active-change.yaml` or a bypassed prior gate), which the current Skill text does not do.
  - **This is not resolved by this analysis** — it is a real design question for the owner: accept the distributed-gate model as satisfying rule 5 (no kit change needed), or require `close-change` to add an explicit self-contained gate-check step (a kit content change, out of this session's current authorization — see `09-proposed-file-diffs.md` for the specific proposed addition, held for a future authorized kit-editing pass). Flagged as a candidate APPLY blocker in the closing summary of this session.
